# Which RAG Reliability Safeguards Are Worth Deploying?

**Proposal for approval.** A service owner can spend an extra inference call checking the evidence before answering, or checking the answer before releasing it. The first check can avoid generation. Only the second sees whether the generator actually made an unsupported claim. Compare both with a baseline already equipped to cite, qualify, clarify and abstain.

## Three customer-facing workflows

Use one fixed text model (proposed GPT-6 Luna, standard tier), no external tools, and the same ordered evidence and question in all stages. Proposed system prompts follow. Before any acquisition, version and hash these strings, fixtures, authority rule, referral, rubric, key and every rendered body. Reconfirm pricing and account availability. No Phase B model responses have been collected.

**Common instruction, prepended to all three prompts:** “Use only the supplied packet. For the requested subject, scope and date, apply the governing source: executed terms over drafts, signed policy over commentary, approved filings over estimates, and a correction over the item it explicitly replaces. A later date alone does not establish authority. Where equally authoritative applicable sources disagree without resolution, identify the conflict. Do not infer missing terms.”

**A · Standard RAG generator:** “Answer the customer. Cite each factual policy or numerical claim with its passage ID. Answer supported parts and identify unknowns. Ask a focused clarification or explain conditional alternatives if needed. You may decline when the packet cannot answer. Never promise an action.”

**B · Pre-generation gate:** “Return exactly PASS if the packet supports a useful answer, supported part, focused clarification, or specific explanation of a documented conflict. Otherwise return BLOCK. Do not answer the customer.” PASS forwards A's exact response bytes. BLOCK displays the fixed referral below. B never sees A's output.

**C · Post-generation verifier:** “Given the customer question, evidence and candidate reply, return exactly PASS if every substantive claim is supported by its cited passage under the authority rules, and the reply respects material qualifications, missing facts and conflicts. A justified abstention or focused clarification may pass without factual citations. Block a gratuitous refusal when the packet clearly supports a useful response. Otherwise return BLOCK. Do not correct, rewrite or answer.” PASS forwards the same A bytes. BLOCK displays the fixed referral. Blocking an over-refusal cannot restore the missing useful answer.

Fixed referral for B and C: “The available evidence does not establish a response I can release. Please ask the responsible desk to review.” Operational errors are recorded as failures. They receive no restraint or verification credit.

## Acquisition, review and decision

One acquisition per stage per question, one layout, no repetitions: 36 generators + 36 gates + 36 verifiers = **108 unique requests** for 108 customer-arm outcomes. C always sees A's response, even when B blocks. Recommended single run covers all three groups; reducing requests by only verifying gates' PASS cases would change the comparison. Precommit order and balanced A/B acquisition order; C follows its generator. Hash each verifier body after binding the immutable generator text into the frozen template. Stop on missing usage, incomplete/malformed stage output, wrong model/tier, integrity or budget failure. Zero retries, no tools or real business actions. Preserve partial records and denominators.

For a prospective budget use at most 2,000 input tokens for A/B and 3,000 for C (including candidate output); allow 512 output tokens for A and 256 each for B/C. Under Phase A planning rates, reserve 252,000 input at $0.25/M and 36,864 output at $0.50/M = **$0.081432**. Propose a **$0.10 ceiling**. Reconfirm rates, exact serialized input bounds including overhead and verifier expansion before approval; stop if the envelope fails. No price or model-access assumption authorizes spending.

Reviewers grade each distinct question/reply once in masked, shuffled order against the packet and key; reuse grades when bytes match. The referral may reveal a block. Record each claim, cited span, applicable subject/date, authority, entailment, contradiction, unsupported extension, citation validity and materiality. Mark useful complete/partial/clarification, justified abstention, or needless refusal. Record disagreements and unresolved grades; have a second reader inspect decision-changing ambiguities where practical. Model verdicts are observations requiring evaluation. Allow roughly half a day to review and reconcile up to 72 distinct responses.

Classify evidence before seeing replies: I03/I11 are designed retrieval misses (answer source exists outside packet); I04/I09 lack proof in the supplied materials; C04/C11 contain unresolved authority conflicts. Grade synthesis errors separately when adequate evidence was offered. For each pair B−A, C−A and C−B report question IDs, actual unsupported replies prevented or introduced, useful answers and clarifications lost, redundant blocks, and retained supported partials. Report groups separately. Weight business severity in a separate sensitivity analysis. Use counts with denominators; a block gets no prevention credit when A already abstained appropriately.

Measure each stage's observed input/output/cache usage, estimated cost, latency and failures. For each question model serial cost and time as A = generator, B = gate plus generator only on PASS, C = generator plus verifier. Sum costs, take medians of per-question modeled serial latencies and paired differences; report acquisition spend separately. Queueing, retrieval and customer handling time require client measurement.

Adopt only when observed preventions address a material failure mechanism and justify lost utility, incremental time and cost under client-specific assumptions. Standard RAG can win; all three can fail on the same authority mistake. Keep Phase A separate. Fictional strata, reused generator draws and one model limit inference about real traffic. Any post-outcome prompt or routing change requires a new frozen set before confirmatory claims.
